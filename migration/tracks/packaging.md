## What each piece does

- **`packaging/macos/bundle.sh <arm64|x64> [--no-build]`** builds `nodus` with `NODUS_PACKAGED=1` and `MACOSX_DEPLOYMENT_TARGET=13.0` for one target, and lays out `dist/mac-<arch>/Nodus.app`: `Contents/MacOS/Nodus` (the app, and the session host as `Nodus host`), `Info.plist` from the template (version = the workspace version, copyright year = the build year), `PkgInfo`, `Resources/icon.icns`. It checks the binary is thin and `minos 13.0`, then signs it with the hardened runtime and `entitlements.plist`: with `NODUS_SIGN_IDENTITY` (the release sets `Developer ID Application`, found in the throwaway keychain) and a timestamp, otherwise ad-hoc. It checks the signing identifier is `dev.saleem.nodus` (so the designated requirement is 0.9.4's, REL-046). With an identity and `APPLE_ID`, `APPLE_APP_SPECIFIC_PASSWORD`, `APPLE_TEAM_ID` all set it notarizes (`notarytool submit --wait`, the status must be `Accepted`, else the log is printed), staples and validates. Secret values are never printed.
- **`packaging/macos/dmg.sh <arm64|x64>`** makes `dist/Nodus-<arch>.dmg` with the same dmgbuild (electron-builder's bundle `dmg-builder@1.2.5`, dmgbuild 1.6.7 with its own Python, downloaded once into `target/packaging/tools` and checked against dmg-builder's SHA-256; `DMGBUILD=` uses another copy) and the same settings JSON dmg-builder 26.15.3 wrote: UDZO, zlib 9, HFS+, volume `Nodus <v>-<arch>`, volume icon `build/icon.icns`, dmg-builder's 540×380 background, window at (400, 530), icons 80/12, `Nodus.app` at (130, 220), `Applications` at (410, 220). Unsigned, as 0.9.4's.
- **`packaging/macos/handoff-gate.sh <dmg> <arch> <version> [<running Nodus.app>]`** replays `src/main/updater.ts` on a DMG with the same argv: `mkdtemp(updates/mount-)`, `hdiutil attach -nobrowse -noautoopen -readonly -mountpoint`, the first `*.app` in directory order, `ditto --noqtn`, `hdiutil detach -force`, `codesign --verify --deep --strict`, the two `plutil -extract … raw` reads against the running copy's bundle id and the version, and the `codesign -dv` TeamIdentifier against the running copy's (skipped when that copy is ad-hoc, as 0.9.4 does). Each failure prints 0.9.4's own message. It also holds the rest of the contract nothing checks at update time: UDZO, unencrypted, no SLA, volume name and HFS+, exactly one `Nodus.app`, the Applications link, volume icon, background and layout, `CFBundleExecutable` = `Nodus`, thin binary of the DMG's arch, `minos` and `LSMinimumSystemVersion` 13.0, no link out of the bundle, hardened runtime, mic and Apple Events entitlements. `GATE_TEAM_ID` (compared, never printed), `GATE_NOTARIZED=1` (stapler validate + `spctl --assess`), `GATE_COPY_TO=<dir>` (keeps the copy 0.9.4 would swap in).
- **`packaging/smoke.py [--open] <exe> [out]`** is `scripts/smoke.mjs` on the D11 driver: own `NODUS_USER_DATA` and `NODUS_AUTOMATION` socket; waits for the window; `1-projects-light.png`; `projects.add` of a temp folder and `2-projects-light.png`; `sessions.create` of an expanded terminal card at (80, 80); the host's protocol-0 welcome must list it (and on Windows carry `host.key`); `echo nodus-$((6 * 7))` must answer `nodus-42`; `3-projects-dark.png`; the driver's `quit` must end the app with 0; then the host gets `shutdown`, the app is killed if still there and `host.log` is copied. `--open` starts the bundle with `open -n --env NODUS_USER_DATA=… --env NODUS_AUTOMATION=…`, as 0.9.4's swap script reopens it (REL-042). The driver has no `sessions.write` or output events yet, so the smoke test types through the host as a second client on the app's protocol. Without the driver (Windows, see below) it checks only that a visible window appears, takes a screen capture and quits the app.
- **`packaging/windows/installer.sh <x64|arm64> [--no-build] [--compile-only]`** builds `nodus.exe` (packaged) into `dist/win-<arch>-unpacked/Nodus.exe`, packs it as electron-builder did (`7z a -mx=9 -mtc=off -mtm=off -mta=off`, `nodus-<v>-<arch>.nsis.7z`), and runs makensis twice exactly as `NsisTarget` did for 0.9.4: same defines in the same order (`APP_ID`, `APP_GUID`/`UNINSTALL_APP_KEY` = `99c2a492-…`, `PRODUCT_NAME`, `PRODUCT_FILENAME`, `APP_FILENAME=nodus`, `APP_DESCRIPTION`, `VERSION`, `APP_PACKAGE_NAME`, `MUI_ICON`/`MUI_UNICON`, `APP_64`/`APP_ARM64` + `_NAME`/`_HASH`/`_UNPACKED_SIZE`, `COMPANY_NAME`, `APP_PRODUCT_FILENAME`, `APP_INSTALLER_STORE_FILE`, `COMPRESSION_METHOD=7z`, `ONE_CLICK`, `RUN_AFTER_FINISH`, `SHORTCUT_NAME`, `UNINSTALL_DISPLAY_NAME`, `ESTIMATED_SIZE`, `COMPRESS=auto`), the same `-X` commands (version keys, `Unicode true`, `SetCompressor zlib`), `-WX -INPUTCHARSET UTF8`, the script on stdin from the templates folder. Pass one (`BUILD_UNINSTALLER`) makes an installer that only writes `Uninstall Nodus.exe`, which is run; pass two embeds it. Templates: `packaging/windows/nsis/` = app-builder-lib 26.15.3's `templates/nsis` byte for byte, with electron-builder's MIT licence. `nsis-header/` = the header and `messages.nsh` electron-builder's own `NsisScriptGenerator`/`nsisLang` generated for Nodus's options (flag macros, the 26 default languages). makensis 3.0.4.1 and nsis-resources 3.4.1 (StdUtils, UAC, WinShell, nsProcess, SpiderBanner, nsis7z, x86-unicode) are electron-builder-binaries' archives, downloaded once and checked against app-builder-lib's SHA-256, or `NSIS_DIR` / `NSIS_RESOURCES_DIR`. `--compile-only` (any OS) checks both passes compile with a stand-in app and uninstaller.
- **`crates/nodus/build.rs`** (Windows targets only): `Nodus.exe`'s icon 0 (`packaging/windows/icon.ico`, made from `build/icon-win.png` by electron-builder 26.15.3's own icon tool: 16…256, PNG entries) and version resource as electron-builder's resource edit wrote it (FileDescription/ProductName `Nodus`, CompanyName `Saleem Hadad`, LegalCopyright `Copyright © <year> Saleem Hadad`, FileVersion `<v>`, ProductVersion `<v>.0`; `SOURCE_DATE_EPOCH` sets the year). The manifest (asInvoker, PerMonitorV2, common controls 6) is GPUI's `windows-manifest` feature. Added build-dependency: `embed-resource` 3.0.12 (already in Cargo.lock through GPUI).
- **`packaging/windows/install-check.ps1`**: a fresh `/S` install (files, HKCU values, both `Nodus.lnk` with description and AUMID `dev.saleem.nodus`, `nodus-updater\installer.exe`, not started without `--force-run`), then the silent uninstall from its own uninstaller keeps `%APPDATA%\Nodus`.
- **`packaging/windows/handoff-gate.ps1 -Old <0.9.4 installer> -New <installer> -Version <v>`**: installs the real 0.9.4 with `/S`, seeds a synthetic `state.json`, copies the new installer to `%APPDATA%\Nodus\updates\Nodus-Setup-<v>.exe` and starts it with exactly `--updated /S --force-run`, then checks: exit 0; `Nodus.exe` is the new version with 0.9.4's kind of version strings; `Uninstall Nodus.exe` there; no Electron files left (`resources`, `locales`, Chromium files); every REL-021 registry value; both shortcuts kept (same timestamps), pointing at `Nodus.exe`, AUMID `dev.saleem.nodus`; `nodus-updater\installer.exe`; `Nodus.exe` started with `--updated` and still running 10 s later; `state.json` kept and read (no `state.json.unreadable-*`).
- **`.github/workflows/package.yml`** (pull requests and pushes to main touching the Rust app or packaging): macOS builds both bundles and DMGs ad-hoc, gates both, smoke-tests the swapped-in copy directly and with `--open`; Windows builds both installers, runs the install check, the handoff gate from the real 0.9.4 x64 installer, and the smoke test. Artifacts: `mac` (DMGs, screenshots) and `windows` (installers, screenshots).
- **`.github/workflows/release.yml`**: see below.

## How to cut a Rust release

1. U1 is settled: `PROTOCOL` is 2 since the cutover (see `cutover.md`).
2. Set `version` in the root `Cargo.toml` `[workspace.package]` to the release version: `X.Y.Z`, newer than 0.9.4 and than the latest release (never `0.9.4.1` or a suffix). Merge to main. The first Rust release is `1.0.0` (the user's pick), already set by the cutover.
3. Rehearse: Actions › **Release** › Run workflow on main, `version` = `X.Y.Z`, `publish` unticked. It checks the version (workspace version, `X.Y.Z`, newer than 0.9.4 and the latest release, not released yet), runs every test, builds and signs both DMGs with the `CSC_LINK` certificate, notarizes and staples, gates 0.9.4's own arm64 DMG (proving the gate) and then each new DMG against that real 0.9.4 copy (same bundle id, same TeamIdentifier, also `APPLE_TEAM_ID`, notarized, Gatekeeper), smoke-tests the swapped-in copy, builds both installers, and on `windows-latest` and `windows-11-arm` installs the real 0.9.4 (x64 → x64, arm64 → arm64, and x64 → arm64 as Windows-on-Arm x64 copies do) and updates it as its updater does. The DMGs and installers are the run's artifacts; try them by hand.
4. Release: run it again with `publish` ticked. Only when every job passed, it creates `vX.Y.Z` as a draft at the run's commit with generated notes, uploads the four assets (`Nodus-arm64.dmg`, `Nodus-x64.dmg`, `Nodus-Setup-x64.exe`, `Nodus-Setup-arm64.exe`), checks each asset is `uploaded` with a `sha256:` digest equal to the file's, publishes it (not a prerelease, marked latest) and checks `releases/latest` now returns it. From then on every installed copy picks it up within 4 hours.
5. Don't publish an Electron release with a higher tag afterwards (that would be a rollback, and needs a still higher version).

Required secrets (names only): `CSC_LINK`, `CSC_KEY_PASSWORD`, `APPLE_ID`, `APPLE_APP_SPECIFIC_PASSWORD`, `APPLE_TEAM_ID`. The workflow refuses to run without them.

## Deliberate differences from release.yml

- Triggered by hand, not by `v*` tags (REL-002), so the Electron release is untouched until cutover. At cutover, either keep it manual or add the tag trigger.
- The release is created as a draft and published only once all four assets are uploaded with their digests (REL-013/REL-014 published first): installed copies never see a release without their asset.
- No JIT or unsigned-executable-memory entitlements (V8 only; WKWebView runs pages in WebKit's own process).
- Info.plist drops `LSEnvironment` (Electron's allocator workaround), `NSPrincipalClass`, `NSMainNibFile`, `ElectronAsarIntegrity`, the `DT*` keys and `app-update.yml`; adds `CFBundleDevelopmentRegion` `en` (no `.lproj` folders).
- The NSIS plugins and makensis aren't vendored as binaries: they're electron-builder-binaries' pinned archives (the exact files 0.9.4 was built with), checked by SHA-256, so no third-party DLLs of mixed licences (StdUtils and nsis7z are LGPL) sit in the repo. Same for dmgbuild.

## Open

- ~~**U1.**~~ Done on `rust/cutover`: `nodus_host_proto::PROTOCOL` is 2, so a Mac app that finds 0.9.4's Node host still running after the swap asks to stop its sessions instead of adopting a host whose `spawn-helper` is gone. Windows is unaffected (0.9.4 stops its sessions before running the installer).
- **The test driver is Unix-only** (`automation.rs` listens on a Unix socket; on Windows it does nothing), so the Windows smoke test only checks the window and quits; REL-034's Ctrl+W checks also need the board. A named-pipe listener in `automation.rs` (ui-shell's file) would make `smoke.py` run fully on Windows unchanged; it already opens the pipe `\\.\pipe\nodus-smoke-<pid>` it names. The driver also lacks `sessions.write` and output events; the smoke test types through the host meanwhile.
- **Needs the real certificate:** the Developer ID signature, notarization, stapling, Gatekeeper, the TeamIdentifier match and the designated requirement (REL-008, REL-009, REL-041, REL-046), and that TCC grants and the `Nodus Safe Storage` Keychain item carry over from an installed 0.9.4 (only a signed build can show it).
- **Needs a Windows run:** everything under Windows above, notably that `Nodus.exe` runs from `%LOCALAPPDATA%\Programs\nodus` on a machine without a WebView2 runtime problem (spec 06 risk 4: a stripped Windows 10 may lack WebView2, and a silent update can't prompt), that the Shell's `System.AppUserModel.ID` property reads back from the shortcut, and that `windows-11-arm` runners have Git Bash and Python.
- x64 macOS is built only by the workflows (no x86_64-apple-darwin target here), so it has not been built yet.
